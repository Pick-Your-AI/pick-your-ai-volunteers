# Review, referral and escalation

The intended order matches [organization routing work #17](https://github.com/Pick-Your-AI/.github/issues/17): authorized team reviewer → repository maintainer → repository lead maintainer → applicable parent-team reviewer → designated organization fallback. The volunteer policy must explicitly authorize each step. A GitHub team maintainer manages membership/settings; that alone gives no selection authority. Four specialty teams are empty, but their interim Project administration is not an accepted volunteer-review mandate.

`data/authority.v2.json` is fail-closed. A reviewer record needs a unique stable numeric `github_user_id`, availability (`available`, `absent`, `conflict`, `unknown`), verification within 30 days, mandate source, allowed actions, approved destinations and escalation approvers. A global activation decision is required; the empty-route fallback also needs explicit approval before use. Unknown, missing, future-dated or stale availability prevents decisions. There is no active deadline or reminder schedule until a response period is approved.

Unavailability means no designated reviewer, recorded absence, a conflict of interest, or an agreed response period expiring. Record the cause and request escalation. A reminder or timeout never accepts an applicant or silently transfers authority. An unavailable reviewer is not required to approve their own replacement: an already designated escalation approver handles the request. Where no mandate/fallback exists, an operator records the governance dependency; nobody guesses authority from a parent team.

Lifecycle: new → awaiting information / awaiting reviewer → accepted → onboarding → active; declined, withdrawn and closed are terminal. Invitation requested, invitation sent and invitation accepted are separate optional steps between onboarding and active. A placement that needs no extra access can complete onboarding directly. Actual invitations remain a manual, separately authorized administrator action with a receipt. Automation never creates invitations or changes permissions.

Referrals enter `referral_pending`; the applicant must use `agree_referral` before the receiving reviewer changes. `decline_referral` retains the current route. Approved reviewer escalation changes only the reviewer, not placement. Reusing any previously visited reviewer is rejected to prevent loops. A new placement after completion requires a new, linked consented application; history is retained.

Pending referrals and escalations retain their originating lifecycle state. Resolving the handoff restores that state, so an active placement remains active after either approval or rejection. Missing origin metadata requires operator reconciliation. Empty-route fallback is selected only by the route resolver; a reviewer cannot claim an unresolved, unavailable, partially specified or conflicting route by submitting an acceptance command.

V2 binds all parties to numeric account IDs and rechecks a pending destination against the current mandate before transfer. Applicant-initiated reviewer escalation also covers accepted, onboarding, invitation and active states when the current reviewer cannot act. A distinct approved receiver/approver arrangement is required; neither a rename nor a pending request creates authority. See [v2 identity and migration](identity-v2.md).

Every accepted transition records old/new state, actor, time, reason, source comment URL and receiving reviewer. Only the GitHub event actor is trusted, never an actor written in command JSON. Duplicate comment IDs do nothing. Invalid commands leave state unchanged. Issue assignees are the current responsible individuals; Project fields must not duplicate ownership. The audit's reviewer is a historical handoff record and must be reconciled with Assignees.

Use `/volunteer {"action":"request_information","reason":"Please clarify your preferred documentation area."}` on the original application. Supported action names are in [the decision schema](../schemas/decision.v1.schema.json). An inactive policy permits applicant withdrawal and cancellation of the applicant's existing pending referral; it cannot authorize a reviewer decision or a transfer. Record ordinary-language requests for operator review; the bot does not interpret them as authorization.

Approved `routes` map canonical selected IDs to ordered role/reviewer steps. Each step requires its own approval reference; moving past an unavailable primary requires `fallback_approved: true`. Conflicting routes from multi-select interests require operator clarification. An explicit Help/No preference choice with no selected scope may use the approved empty-route fallback. A named selected scope with no route or an empty route remains unresolved. The resolver never derives a mandate from team membership.
