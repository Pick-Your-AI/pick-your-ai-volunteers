# Operator guide

Read the organization contribution rules and prior-work register. Maintain this hub through reviewed PRs; do not alter research owners or contracts. Issue forms label application, opportunity, referral and availability records separately. The public Project uses Kind, Volunteer state, Staffing need and Readiness fields, with built-in Assignees as canonical responsibility.

On intake, review public-safe content and scope. If someone posts sensitive details, use existing organization moderation procedures; do not copy details into logs, exports or Project fields. The bot creates an append-only state comment but does not promise a response. Find applications through the saved Project views or issue labels. The Project synchronization command is `python scripts/project_sync.py`; it uses the authenticated GitHub CLI. It adds only this hub's public issues and writes categorical fields, never copies issue bodies into Project text fields. Run after decisions until a narrowly scoped Project credential is explicitly installed. The ordinary GITHUB_TOKEN does not provide organization Project access.

Governance activation checklist: obtain an organization decision naming reviewer mandates, fallback authority, approved routes and a response period; get each reviewer's availability confirmation; edit data/authority.v1.json by PR; run all checks; obtain independent approval of the final head. Existing team nesting, repository permissions or issue assignment alone cannot approve this change. The policy's enabled flag is currently false. Scheduled reminders and automated decisions dependent on missing authority remain inactive.

When active, issue-comment commands are validated against trusted actor metadata and the current default-branch policy. Never interpolate issue bodies into shell commands. Changes to scripts execute only from the default branch on intake. Workflow permissions are contents:read and issues:write; CI is contents:read. The bot may assign only an authorized receiving reviewer; it cannot grant access. Check rejected runs for the generic failure signal, without printing submitted content. Reconcile Assignees against the latest successful audit comment; manually changed Assignees do not change the recorded mandate.

If an audit comment posts but assignment or Project update fails, preserve that comment. Rerun synchronization and reconcile Assignees to its authorized recipient; do not replay a new decision ID. Keep all audit comments; deletions or edits invalidate the audit chain and require manual incident review. GitHub issue history is an operational audit, not immutable or tamper-proof storage. Backups containing applicant content need a separately approved retention/access policy; none is installed here.

Refresh public directory relationships using authenticated paginated GitHub reads, review additions/removals and preserve stable IDs. Do not export membership identities or restricted repositories. Verify team and repo relations separately from operational authority. A 30-day freshness threshold intentionally fails closed; do not merely bump dates without source checks. Capacity updates require evidence and a reviewed canonical change. No recurring membership scrape or automatic policy rewrite is installed.

Project views should show: New applications; Awaiting information; Awaiting escalation approval; Awaiting reviewer (including missing reviewer); Accepted/onboarding; Active placements; Closed/declined/withdrawn; Open opportunities; Priority staffing; Missing leadership/onboarding. Application state is independent of opportunity recruitment. Opportunity records must be updated when capacity changes; an accepted person does not automatically fill a vacancy count.

The worker checkpoints IDs of both accepted and rejected commands so a later authority change cannot silently replay an old rejected request. It replays unseen commands in API order after GitHub concurrency replaces a pending run. Rejected commands expose no input in logs.

The manual Project workflow is present but cannot run successfully until `VOLUNTEER_PROJECT_TOKEN` is provisioned. No credential was copied from an operator account. Use a dedicated, narrowly scoped, approved credential; the CLI synchronizer already works with an authorized operator session. This is a manual workflow, not a scheduled automation.

Route records use `role`, `reviewer`, `approval_reference` and `fallback_approved`, with roles in the documented sequence. Give each selected entity an approved route or leave it unresolved. Correct a rejected or edited command using a new comment; processed IDs are not replayed.
