# Operator guide

Read the organization contribution rules and prior-work register. Maintain this hub through reviewed PRs; do not alter research owners or contracts. Issue forms label application, opportunity, referral and availability records separately. The public Project uses Kind, Volunteer state, Staffing need and Readiness fields, with built-in Assignees as canonical responsibility.

On intake, review public-safe content and scope. If someone posts sensitive details, use existing organization moderation procedures; do not copy details into logs, exports or Project fields. The bot creates an append-only state comment but does not promise a response. Find applications through the saved Project views or issue labels. The Project synchronization command is `python scripts/project_sync.py`; it uses the authenticated GitHub CLI. It adds only this hub's public issues and writes categorical fields, never copies issue bodies into Project text fields. Run after decisions until a narrowly scoped Project credential is explicitly installed. The ordinary GITHUB_TOKEN does not provide organization Project access.

Governance activation checklist: obtain an organization decision naming reviewer mandates, fallback authority, approved routes and a response period; get each reviewer's availability confirmation; edit data/authority.v2.json by PR; run all checks; obtain independent approval of the final head. Existing team nesting, repository permissions or issue assignment alone cannot approve this change. The policy's enabled flag is currently false. Scheduled reminders and automated decisions dependent on missing authority remain inactive.

When active, issue-comment commands are validated against trusted actor metadata and the current default-branch policy. Never interpolate issue bodies into shell commands. Changes to scripts execute only from the default branch on intake. Workflow permissions are contents:read and issues:write; CI is contents:read. The bot may assign only an authorized receiving reviewer; it cannot grant access. Check rejected runs for the generic failure signal, without printing submitted content. Reconcile Assignees against the latest successful audit comment; manually changed Assignees do not change the recorded mandate.

If an audit comment posts but assignment or Project update fails, preserve that comment. Rerun synchronization and reconcile Assignees to its authorized recipient; do not replay a new decision ID. Keep all audit comments; deletions or edits invalidate the audit chain and require manual incident review. GitHub issue history is an operational audit, not immutable or tamper-proof storage. Backups containing applicant content need a separately approved retention/access policy; none is installed here.

Refresh public directory relationships using authenticated paginated GitHub reads, review additions/removals and preserve stable IDs. Do not export membership identities or restricted repositories. Verify team and repo relations separately from operational authority. A 30-day freshness threshold intentionally fails closed; do not merely bump dates without source checks. Capacity updates require evidence and a reviewed canonical change. No recurring membership scrape or automatic policy rewrite is installed.

Project views should show: New applications; Awaiting information; Awaiting escalation approval; Awaiting reviewer (including missing reviewer); Accepted/onboarding; Active placements; Closed/declined/withdrawn; Open opportunities; Priority staffing; Missing leadership/onboarding. Application state is independent of opportunity recruitment. Opportunity records must be updated when capacity changes; an accepted person does not automatically fill a vacancy count.

The worker checkpoints the highest processed comment ID so a later authority change cannot silently replay an old rejected request. It replays unseen commands in ascending ID order after GitHub concurrency replaces a pending run. Each accepted transition has its own bounded audit delta; rejected commands share a cursor checkpoint. Read all trusted ledger comments for complete history. Rejected commands expose no input in logs.

New intake initializes form consent and canonical selections from the trusted applicant opening event or a fresh applicant-authored recovery confirmation. Comment-first recovery requires a fresh applicant-authored `/volunteer-apply` confirmation; a later issue body cannot prove consent. Pre-confirmation applicant withdrawal records a minimal terminal state without treating it as consent. The [recovery procedure](identity-v2.md) gives exact instructions. Commands are limited to 8,192 characters and 16 JSON nesting levels. Invalid or edited commands are checkpointed without echoing their content; submit a fresh comment to correct a command. Creation/update timestamps must match. A visibly edited bot ledger, any trusted v1 ledger, or missing v2 initialization/identity/consent/cursor metadata stops for manual reconciliation; automation does not reset historical decisions. These checks cannot prove that all deleted or otherwise undetectably modified comments still exist: GitHub comments remain an operational audit, not tamper-proof storage.

Reviewer assignment uses the additive endpoint and preserves existing assignees. An approved handoff does not remove the previous reviewer or an unrelated owner; an authorized operator reconciles removals separately against the audit history. A new, unassigned application retains its canonical selections. After an actual governance activation, its next reviewer command reruns the route resolver with the current approved policy and accepts only the resolved receiver. Unavailable, partial and conflicting routes stay blocked; no reviewer can substitute the empty-route fallback. Do not edit a historical bot comment to manufacture a routing decision.

The manual Project workflow is present but cannot run successfully until `VOLUNTEER_PROJECT_TOKEN` is provisioned. No credential was copied from an operator account. Use a dedicated, narrowly scoped, approved credential. The CLI synchronizer can use a separately authorized operator session; the current v2 identity path has only mocked offline verification and still needs separately authorized live readback. This is a manual workflow, not a scheduled automation.

Project synchronization validates affirmative application consent before item creation; skipped or failed intake cannot become a Project application. Transport failures stop processing for readback, never overwrite a possibly committed transition with a rejected-command snapshot.

Route records use `role`, `reviewer`, `approval_reference` and `fallback_approved`, with roles in the documented sequence. Give each selected entity an approved route or leave it unresolved. Correct a rejected or edited command using a new comment; IDs at or below the durable cursor are not replayed.

Read the [v2 identity, consent and migration contract](identity-v2.md) before changing authority. Every reviewer mandate needs a unique `github_user_id`; aliases and account logins cannot substitute for it. The enabled policy must include the approved response period. Applicant withdrawal survives account renames. Handoff completion rechecks current destination authorization and account identity; past approval does not preserve a revoked mandate. Invitation receipts are operator attestations, not independently verified deliveries.
